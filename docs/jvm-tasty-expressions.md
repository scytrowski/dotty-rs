# Bounded JVM/TASTy expression parity

This records the #2470 increment. The
[numeric-ascription contract](jvm-tasty-numeric-ascriptions.md) extends its
ascriptions to canonical Long/Float/Double values. The subsequent
[guarded-match contract](jvm-tasty-guarded-matches.md) extends its match subset
with guards and immutable Int pattern bindings.

This increment targets Scala 3.9.0 revision
`777528f19a58e794c9954a42f433373472ec57f8`, TASTy 28.9.0 and JVM class-file
major 65. Both producers must consume the same canonical source session.

The scope is primitive Int/Boolean/Unit ascriptions, Int bitwise `&`, equality
and inequality between two Int values, and Int-selector matches with literal
cases and a final unguarded wildcard. Match results are Int, Boolean or Unit.
Patterns with binders, guards, extractors, runtime type tests and matches
without a final wildcard remain unsupported. There is no general erasure,
reference equality or runtime cast increment here.

The independently compiled source is
`tests/fixtures/jvm_tasty_expressions/Expressions.scala`. Its `oracle.txt`
and `provenance.json` are generated by the adjacent `run.py`, which reuses the
existing pickler oracle's offline toolchain and artifact hash checks:

```sh
SCALA39_ROOT=/path/to/pinned/scala3 JAVA_HOME=/path/to/jdk21 \
COURSIER_MAVEN_ROOT=/path/to/cached/maven \
python3 tests/fixtures/jvm_tasty_expressions/run.py
```

The Scala-produced TASTy dump is reference evidence, not Rust output or proof
that the Rust producers accept these expressions. Each implementation commit
adds independent producer regressions; final acceptance must read and execute
the actual Rust artifacts with the pinned Scala compiler and JDK verifier.

## Implemented contract

Ascriptions require a canonical Int, Boolean or Unit type, the exact mapped
type tree, and a compatible child expression. The JVM path emits no conversion;
the pickler retains TYPED and its explicit type syntax. Annotated types,
reference casts and unsupported primitive conversions are rejected.

Int conjunction resolves the registered Int operator and emits `iand` after
the receiver and argument have each been evaluated once in source order.
Equality uses the existing canonical Any equality symbols and validates their
original `(Any): Boolean` signatures. For two Int operands only, JVM emission
uses `if_icmpeq`/`if_icmpne` and the TASTy projection emits Scala 3.9's observed
Int-owned signed `(Int): Boolean` selection. This specialization neither
changes the source symbol nor creates a second equality declaration.

Matches retain source case order. Literal cases precede exactly one final
unguarded wildcard. JVM lowering stores the selector in one temporary Int slot
and uses conditional branches; it intersects initialization facts across
normally completing cases. TASTy retains MATCH, CASEDEF, literal patterns and
the typed wildcard. Bodies use the existing supported expression subset.
Standalone JVM expression APIs without a planned local layout cannot allocate
the match selector slot. Producer item limits are checked before copying
untrusted case vectors; ordinary depth and expanded-node budgets still apply.

The one-class paired adapter passes the typer's exact ordinary local bindings
to both producers, including inferred Int declarations. The shared contract
rejects disagreements in Int local symbols, typed declarations and mutability
through `LocalBindingMismatch`. Both plans borrow the same store and arena;
validation remains read-only, and no partial artifact pair escapes failure.

## Independent execution gate

`tests/jvm_tasty_expressions.rs` covers exact ascription bytecode, signed
operator signatures, ordered case counts, unsupported patterns, malformed type
trees, missing local evidence and byte-for-byte determinism in fresh sessions.
Its JDK gate executes the original composed fixture and separate effectful
operands, checking left-to-right evaluation and one evaluation per operand.

With `DOTTY_REQUIRE_SCALA_TASTY_CONSUMER=1`, the test writes the genuine Rust
pair and invokes the adjacent oracle runner. The runner checks the pinned
source revision and eight compiler/runtime JAR hashes, reads the Rust TASTy,
compiles an independent Scala client against the original pair, and recompiles
the sidecar with `-from-tasty`. Independent Java execution checks both the
original Rust class and the class reconstructed by Scala, using
`java -Xverify:all -ea`. Every consumer uses separate output; the original pair
is checked unchanged afterwards.

The composed runtime matrix covers Int boundaries and signed inputs, both
Boolean values, literal and wildcard paths, Unit effects, one selector
evaluation, inferred local storage, and the composed mask/equality/match body.
Two fresh Rust sessions produce identical bytes and UUIDs. One local acceptance
run on JDK 21.0.13 recorded:

| Original Rust artifact | SHA-256 |
| --- | --- |
| `example/Expressions.class` | `8d5d95d5ee0c4633e8d77f4103d5a26e30b415c2dc8663310d8e42940e09e4ba` |
| `example/Expressions.tasty` | `98df632e4f53edf710c938b0321dac39c339b14643cca6810f57d01c3d35c82d` |

All three execution paths report `expression parity ok`. These are semantic
and runtime checks; the Rust output is not byte-identical to Scala output.

Reproduce the strict target with the same environment as the oracle command:

```sh
DOTTY_REQUIRE_SCALA_TASTY_CONSUMER=1 DOTTY_CLASSFILE_REQUIRE_JDK=1 \
cargo test --test jvm_tasty_expressions --locked -- --nocapture --test-threads=1
```

The target is registered once in `tools/ci/strict_tasty_targets.json`, on
shard 3, and in the ordinary JDK verifier gate. The existing four strict shards,
aggregate and follow-up gates remain required; no full Scala corpus is enabled.
